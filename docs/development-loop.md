# Daemon and terminal development loop

The distribution uses the repository-selected Spice toolchain as two separate
development supervisors. Start each target in its own terminal:

```text
make dev-daemon
make dev-terminal
```

Start `dev-daemon` first. Development candidates are intentionally isolated
build artifacts and do not copy a sibling daemon binary into the terminal's
temporary build directory; the terminal's managed mode therefore discovers and
attaches to the daemon already supervised by `dev-daemon`.

`dev-daemon` builds the `spice-agentd` target from `cmd/spice-agentd` and
passes `serve` to the candidate. `dev-terminal` builds the `spice-agent` target
from `cmd/spice-agent` and runs its managed attach-or-start mode. Both targets
are package-main Spice applications, so the supervisor builds the complete
package with committed generated Go rather than a source fragment.

The selectors above are the shipped command names. Spice normalizes their
portable manifest IDs and generated-package suffixes to `spice_agentd` and
`spice_agent`; users still install and invoke `spice-agentd` and `spice-agent`.

Each supervisor owns its own monotonically revised candidate stream and
last-known-good process. Analysis, generation, or compilation failure in one
stream leaves that stream's current process running. A later valid candidate
gracefully replaces only the process owned by that supervisor. Stopping one
supervisor does not stop the other; the terminal may reconnect to a compatible
daemon after a daemon restart.

The Make targets exclude source directories and generated ownership artifacts
owned solely by the other product target. A daemon-only edit therefore does
not restart the terminal, and regeneration of that daemon does not wake the
terminal supervisor merely because generated bytes changed. The inverse holds
for terminal edits. Shared configuration, module, transport, process, and
dependency files remain visible to both watchers by design because they can
affect both generated graphs.

The first development run requires the same configuration as its executable.
In particular, the daemon requires `OPENAI_API_KEY`; Spice redacts that value
from diagnostics and generated state. Coding tools retain the current user's
filesystem and process authority and are not sandboxed.

The last-known-good, debounce, unique-candidate, graceful-stop, and bounded
escalation implementation belongs to `spice-framework/toolchain`. This
repository's acceptance boundary proves that both distribution targets use the
required application-package layout and that their exact generated packages
and command adapters build together. A complete fault-injection workflow that
edits source while both real terminal processes are attached remains a Phase 5
end-to-end acceptance item.
